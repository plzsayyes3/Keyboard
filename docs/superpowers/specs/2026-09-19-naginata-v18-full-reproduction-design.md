# 薙刀式v18完全再現・出典表示 設計仕様

## 1. 目的

大岡俊彦氏の薙刀式v18トップ版を、手作業で抜粋した配列ではなく、公式定義を機械的に読み込んだ練習用データとして再現する。単文字・単語・短文のすべてを同じ入力パイプラインで判定し、ユーザーのBeThirty用配列も別プロファイルとして切り替えられるようにする。

画面には、使用した公式資料とユーザー提供設定を明示する。実装は静的サイトで完結し、OSのIMEやQMKの設定を変更しない。

## 2. 資料の優先順位と来歴

配列データの根拠は次の順序で固定する。

1. リポジトリ内の `data/reference/naginata-v18.txt`。公式定義を取得したCP932テキストであり、生成処理の直接入力とする。
2. 大岡俊彦氏のv18トップ版マニュアルPDF。リポジトリ内にPDF本体がない場合も、公式URLを出典として表示し、テキスト定義との照合根拠にする。
3. 大岡氏の薙刀式紹介・v18発表記事。
4. ユーザー提供のBeThirty Ortho設定。標準配列の訂正資料ではなく、ユーザー配列プロファイルの根拠として扱う。

生成JSONには、配列名、版、生成元ファイル、生成元ハッシュ、生成日時ではなく再現可能な固定メタデータ、各エントリの出典セクションを含める。公式定義に対応付けられない行は黙って捨てず、ビルドを失敗させる。

## 3. 公式v18の再現範囲

公式テキストに存在する全セクションを対象にする。

- 清音の単打
- センターシフト
- 濁音
- 半濁音
- 小書き文字
- 清音の拗音
- 濁音の拗音
- 半濁音の拗音
- 外来音
- IMEオン・IMEオフ
- Enter、削除、カーソル等の機能キー
- 編集モード切替
- 公式定義にある固有名詞・ショートカット

「文字を返す定義」と「操作を返す定義」を同じ配列エントリに詰め込まず、出力種別を分ける。

```json
{
  "keys": ["KeyJ", "KeyF"],
  "output": { "type": "text", "value": "が" },
  "source": { "section": "dakuten", "line": 123 }
}
```

操作出力は `imeOn`、`imeOff`、`enter`、`backspace`、`arrowLeft` などの固定アクション名で表す。ブラウザはOSへ操作を発行せず、練習画面上で期待操作として表示し、入力結果として記録する。

## 4. 生成データの構成

公式テキストの表記ゆれを吸収する専用パーサーを追加する。

- `scripts/build-naginata-layout.mjs`: CP932の公式テキストを読み、別名・物理キー・出力・セクションを解決する。
- `src/engine/naginata-definition-parser.js`: パーサーの純粋な解析処理。Nodeテストからも呼べるようDOMに依存しない。
- `data/layouts/naginata-v18.json`: ブラウザが読む生成成果物。直接編集しない。
- `data/layouts/user-current.json`: BeThirty Orthoのユーザー配列。標準生成データから自動上書きせず、差分とメタデータを保持する。

生成JSONの最上位には `schemaVersion`、`layoutVersion`、`generatedFrom`、`sourceHash`、`entries`、`controls` を置く。複数候補、明示的な別名、機能出力、未解決行を区別して保存する。

## 5. 同時押しと順序

薙刀式の同時押しは「キー集合」と「押下順序」を別の情報として保持する。集合をソートして正規化してはならない。公式定義で順序が意味を持つ場合はその順序を正本とし、逆順を自動的な同義語にしない。公式上順序非依存と確認できる定義だけ、必要なら逆順候補を明示的に生成する。

サイト内変換モードは次の状態機械で処理する。

1. `keydown` で `KeyboardEvent.code` を押下集合へ追加する。
2. 同時押し受付中はキーを離しても確定せず、設定した同時押し窓とキー集合を保持する。
3. センターシフトを含むコードは、最後に離したキーを含む順序付き候補として照合する。
4. `keyup` で成立候補が一つに決まった時だけ、かなまたは操作を1出力として確定する。
5. 未登録の集合・順序は入力エラーとして記録し、次の課題へ進めない。

これにより、単文字だけでなく、濁音・拗音・外来音・単語・短文でも「物理入力→出力列→課題比較」の経路が同じになる。

## 6. 二つの入力モード

### 変換済み入力モード

QMK、OS、IMEなどがすでに生成した文字を受け取る。`beforeinput` と `input` を中心に出力文字列を正規化し、NFC、改行、空白、長音、かなの境界を壊さず課題の残り文字列と逐次比較する。ひらがな一文字単位に限定せず、複合文字列を受け取っても課題インデックスを正しく進める。

### サイト内変換モード

通常QWERTY、ノートPC、自作キーボードのいずれでも、`KeyboardEvent.code` を物理キー識別子として使う。キーの見た目やOS配列に依存せず、layout mapping層で表示名と物理コードを分離する。`KeyboardEvent.key` のローマ字値は物理判定に使わない。

ブラウザの制約上、サイトはOS/QMK/IMEの設定を変更できない。実際のOS動作は利用者側に任せ、サイト内変換モードではキーイベントを採点用に解釈する。

## 7. ユーザー配列プロファイル

ユーザー設定として次を記録する。

- BeThirty Ortho、4x10、7レイヤー、エンコーダなし
- レイヤー0はQWERTYを維持
- 薙刀式の実装レイヤーは5
- 基本かなのユーザー指定（J/K/L、W/E/R、I/O、F/D/H、N/M/Comma）
- 濁音・拗音等は標準v18準拠
- HJで有効、GFで無効という実機モード情報
- TD0/TD1のタップ・ホールド設定
- Unicode有効

この情報は「サイトが受け取る物理キー」と「実機が変換済み文字を出力する場合の説明」を混同しないよう、`hardwareConfig` と `layoutEntries` に分ける。

## 8. セッション判定

課題は `target` 文字列、正規化済み入力列、現在インデックスを持つ。単文字・単語・短文にかかわらず、出力イベントを課題の残り部分と比較する。正しい接頭辞ならその長さだけ進み、途中に不一致があればそのイベント全体を誤入力として記録する。誤入力後に正しい文字が続いた場合も、課題文字を勝手に消費しない。

画面には常に次を表示する。

- 目標: 課題全体
- 入力: 現在までに受け付けた入力
- 現在の期待文字または操作
- 実際に受けた直近の入力
- 正誤、進捗、正解数、誤入力数、正確率
- 現在の候補キーと、押下中キー

正確率は小さく表示し、目標と入力の比較を主役にする。

## 9. 参考資料・出典UI

練習画面の下部に折りたたみ可能な「参考資料・出典」欄を置く。各行に資料名、著者、役割、URL、参照対象を表示する。

- 公式マニュアルPDF: 全定義の一次資料
- 公式v18発表記事: 版と変更点
- 薙刀式紹介記事: 配列の背景
- リポジトリ内公式定義テキスト: 生成処理の入力
- ユーザー提供BeThirty設定: ユーザー配列の根拠

配列セレクタを変更した時は、その配列に対応する出典も表示する。公式資料とユーザー設定を「公式」として混ぜない。

## 10. 検証と受け入れ条件

実装前に、公式テキストの各セクションをパーサーのfixtureで検証する。少なくとも次を自動テストする。

- 清音、センターシフト、濁音、半濁音、小書き、3キー以上の拗音、外来音
- 公式の機能キー出力と出力種別
- `が` のユーザー確認済みキー順、`しょ`、`じょ` 等の既知例
- 同じキー集合で順序が異なる定義の衝突
- 未解決行・重複定義・空出力をビルドエラーにすること
- 生成JSONのエントリ数と各公式セクションの網羅性
- 変換済み入力モードで単語・短文を最後まで正しく進めること
- サイト内変換モードで同じ単語・短文を物理イベントから最後まで進めること
- 標準配列とユーザー配列の切り替え、出典欄の表示

受け入れ条件は、公式テキストにある定義を未報告のまま落とさないこと、単文字・単語・短文が同一のセッションロジックで成功すること、ブラウザ確認で配列切替・モード切替・目標/入力表示・出典表示が成立することである。

## 11. 制約と未確定事項

現在リポジトリには公式PDF本体ではなく、CP932の公式定義テキストがある。実装はこのテキストを機械可読化し、公式PDFへのリンクを出典として掲載する。PDFバイナリをリポジトリへ同梱するかどうかは、ライセンスと配布上の確認が取れるまで決めない。

公式定義におけるOS依存の編集動作は、サイト内で「期待操作」として再現する。実際のIME切替や漢字変換までブラウザから保証するものではない。
